:::meta description: How to give Luccet's element names meaning, look and behaviour: the schema and every schema field, window.LUCCET.schema, add-ons, luccet.define, custom transforms, styling, and labels in other languages. ::: ::site-nav # Vocabulary and behaviour {#top} ::toc Luccet's core knows how a name is *written*, as in `:::theorem`, `::toc` or `:kbd[Ctrl]`, but not what it *means*. A **schema** gives names their meaning: the element, a label such as "Theorem 2", a counter, how a reference reads, a title slot, an end mark, a table of contents. The schema's `css` and `dom` fields, `luccet.style` and `luccet.define` give them a look and a behaviour. This page covers all of it, from a note that declares three names in its head to an add-on shared by a hundred notes. The live examples run with **no schema** unless they say `schema=demo`. The demo schema is the small vocabulary listed at the [end of this page](#demo-schema). ## Why names need a schema {#why} The core gives a name no meaning. `:::theorem` is `div.t-block.theorem` until a schema says otherwise: no label, no number, and a reference to it reads its title. ```luccet {.live} :::theorem[Rank–nullity]{#rn} $\dim V = \dim \ker T + \dim \operatorname{im} T$. ::: See @rn. ``` The same note with the demo schema, which declares `theorem`: ```luccet {.live schema=demo} :::theorem[Rank–nullity]{#rn} $\dim V = \dim \ker T + \dim \operatorname{im} T$. ::: See @rn. ``` The difference is one entry: ```js theorem: { tag: 'section', counter: 'theorem', label: 'Theorem', ref: '{label} {n}' } ``` **Why the core declares nothing.** Every subject needs its own names: a lecture has theorems, a lab notebook has protocols, a cookbook has steps. Labels differ from one language to the next. And a note must render from one script line, without a standard library to keep in step with it. So a note, or an add-on it loads, declares exactly the names it uses. A name without an entry still renders. It keeps its class and its `data-t`, so CSS and behaviours can find it, and it becomes an element on its own when the name is one: - an allowlisted element: `:::aside` is an `
`; - a custom element: `:::tide-panel` is a ``. [Elements and output](elements.html#names) has the whole resolution. :::table[What a schema entry adds]{#tbl-adds} | | Without an entry | With an entry | |---|---|---| | Element | `div` or `span`, or the name itself when it is an element | `tag` | | Classes and attributes | `t-block`, the name, the author's | `class`, `attrs` | | Label | none | `label` | | Number | none | `counter` | | Reference text | the title, else the id | the label and number, through `ref` | | Title element | written titles only | `title`, `titleDefault`, and a slot for the label | | End mark | none | `end` | | Body | blocks, or verbatim with `{raw}` | `body` | | Generated content | none | `transform: 'toc'` | | Look | the base stylesheet | `css` | | Behaviour | `luccet.define` only | `dom` | ::: **Where vocabulary comes from.** 1. **The note's own head:** `window.LUCCET.schema`, in a script before the luccet.js line ([below](#window-luccet)). Best for a note that stands alone. 2. **An add-on** listed in `data-use`, which calls `luccet.block`, `luccet.leaf` and `luccet.inline` ([Add-ons](#addons)). Best for vocabulary shared by several notes. 3. **Node**, for scripts that call the engine: the same three functions, or a `schema` option on each call ([JavaScript API](api.html#registry)). When a note and an add-on declare the same name, the note's entry wins. ## The schema {#schema} ### The registry {#the-registry} A schema is plain data: an object with three levels, each mapping a name to an entry. ```js { block: { theorem: { tag: 'section', counter: 'theorem', label: 'Theorem' } }, leaf: { toc: { tag: 'nav', transform: 'toc' } }, inline: { key: { tag: 'kbd' } }, } ``` In the browser this object is `luccet.schema`, the registry. Three functions write it: :::syntax ```js luccet.block(name, spec) // :::name … ::: luccet.leaf(name, spec) // ::name[…]{…} luccet.inline(name, spec) // :name[…]{…} ``` ::: - **The entry.** Each function stores a shallow copy of `spec` and returns it. Changing your `spec` object afterwards changes nothing; changing the stored entry does: `luccet.schema.block.note.label = 'Hinweis'`. - **Again.** Registering a name a second time replaces its entry whole. - **Refused.** They throw a `TypeError`, and register nothing, when: - the name is not a NAME: a letter, then letters, marks, digits, `_` or `-`; - the name is reserved: `base body head html link main meta noscript script style template title`, `luccet`, any `t-…` name, and `end`; - a block name is one of the core containers `meta`, `macros`, `script`, `style` or `html`; - `spec` is not an object. - **When.** The registry is read each time a note is rendered. Declare entries in an add-on or in `window.LUCCET.schema`: both are applied before the note is mounted. A ` ::toc ## The theorem :::theorem[Rank–nullity]{#rn} $\dim V = \dim \ker T + \dim \operatorname{im} T$. ::: :::proof Extend a basis of $\ker T$ to a basis of $V$. ::: ## Using it By @rn, … Press :key[Ctrl]. ``` The toc is a `nav` with two entries, the theorem a `section` labelled "Theorem 1", the proof ends with ∎, `@rn` reads "Theorem 1", and `:key[Ctrl]` is a ``. :::note The examples in this section are source, not live. A live example renders with the engine alone, and `luccet.toHTML(source, {head})` reads the head only for what `:::meta` and the labels need: its ``, the `lang` and `dir` of `<html>`, and its `<meta name>` tags. It runs no script. Running the head's scripts is the job of the browser runtime and the command line. Under node, pass the vocabulary as the `schema` option instead. ::: **The rules.** - **Shape.** `window.LUCCET.schema` holds `block`, `leaf` and `inline`, each optional, with entries as for `luccet.block`. Function fields (`label`, `dom`) and `css` work as in an add-on. - **Where.** In a classic `<script>` before the luccet.js line: inline, or a `src` file of your own (`<script src="vocabulary.js">`). luccet.js reads `window.LUCCET` when it starts. The command line runs only classic head scripts, not `async`, `defer` or module ones. - **When.** At mount, after every add-on has registered its entries. Each entry goes through `luccet.block`, `luccet.leaf` or `luccet.inline`. - **Precedence.** So the note's entry replaces an add-on's entry for the same name, **whole**: the fields are not merged. An add-on's `dom` for that name is gone, unless the note's entry has one too. - **A bad entry** (a reserved name, a value that is not an object) is skipped with a warning in the console; the others apply. - **The levels and `strict`** are read: `strict: true` turns on [strict names](#strict), and `strict: false` turns off an add-on's. `window.LUCCET` carries other settings too, such as `lang`, `use` (the add-ons' options) and `macros` (TeX macros for every formula; [Configuration](api.html#config)). - **Built pages.** `luccet build` applies the vocabulary when it writes the HTML. luccet.js applies it again when the built page starts, for the behaviours and for `luccet.render`. **Under node.** `luccet check`, `luccet parse`, `luccet build` and the language server run the head's scripts in a sandbox, in document order, before the add-ons. Then `window.LUCCET.schema` goes on top, as in the browser. - An inline script, or a `src` file on disk, runs. - A remote `src` is not run: `head.script` (info). - A missing file, or a script that throws, gives `head.script` (warning). **Changing one field of an add-on's entry.** A note's own entry replaces the add-on's whole. To change one field and keep the rest, list a small add-on of your own after it in `data-use`, and assign into the registry: ```js // tweaks.js, listed after the add-on: data-use="callout.js tweaks.js" luccet.schema.block.note.label = 'Hinweis'; ``` **Diagnostics:** [`head.script`](diagnostics.html#head-script), from the command line and the language server only. ## Add-ons {#addons} An add-on is a script or a stylesheet a note lists in `data-use` or `:::use`, to add vocabulary, behaviour and a look. [Add-ons](addons.html#top) lists Luccet's own, and [Writing an add-on](addon-api.html#top) is the contract one of your own can rely on: how it loads and takes options, what it registers, the lifecycle, math, foreign content and the command line. ## Behaviours {#behaviours} A behaviour is a function the runtime calls for each element of a name, after the note is in the page: to add a button, start a widget, read the element's data. ### `luccet.define` {#luccet-define} :::syntax ```js const undo = luccet.define(name, fn) // fn(el), with this === el luccet.undefine(name) ``` ::: ```js luccet.define('countdown', (el) => { const days = Math.ceil((new Date(el.dataset.to) - Date.now()) / 864e5); el.textContent = `${el.dataset.label}: ${days} days`; }); ``` - **Keyed on `data-t`.** `fn` runs for every element whose `data-t` is `name`: containers, leaves and inline elements, with or without a schema entry, and every fence (`data-t="code"`). A bare span `[x]{…}` has no `data-t`. - **Once per element** and function. Elements are remembered, so `luccet.render()` never runs a function twice on one element. - **Document order**, element by element. For each element: its schema `dom`, then each `define` function for its name, in registration order. - **Math is there.** Formulas are already MathML when behaviours run. An add-on that renders math itself does it later, in a `render` listener: see [Behaviours that need rendered math](#pattern-math). - **Additive.** Several functions per name all run. - **`undo()`** removes that one function, for elements met afterwards; what it did to earlier elements stays. - **`luccet.undefine(name)`** removes every function `define` registered for the name. A schema `dom` stays. - **Late.** A function defined after the behaviours ran, in a `ready` listener for example, runs at once on the elements already in the page. - **Errors** are caught and logged (`luccet: the "name" behaviour failed`); the other behaviours go on. - **Arguments.** A name that is not a non-empty string, or an `fn` that is not a function, throws a `TypeError`. - **Where.** In an add-on, or in a `<script>` in the note: note scripts run after the mount and before the behaviours. - **Under node** `define` is accepted and never runs. What a behaviour can find: a leaf and a fence carry `data-t`, a bare span does not. ````luccet {.live} ::countdown{data-to=2026-12-31 data-label="New year"} ```js console.log('a fence'); ``` A [bare span]{.aside}. ```` ### A `dom` function in a schema entry {#dom-function} A schema entry's `dom` is a behaviour declared with the vocabulary: same signature, same rules. - **It runs first** on its element, before the `define` functions. - **One per element.** The runtime looks for a `dom` level by level and runs the first it finds. For an element with the class `t-block` (a container, or a titled fence) the order is block, leaf, inline; for any other, leaf, inline, block. So both an untitled fence (`pre`) and a titled one (`figure.t-block`) find `block.code`'s `dom`, unless a leaf or inline entry named `code` has one. - **`window.LUCCET.schema`** may hold `dom` functions too. - **`luccet.undefine`** does not remove it. ### Events {#events} :::syntax ```js const off = luccet.on(event, fn) ``` ::: :::table[Events]{#tbl-events} | Event | When | `fn` receives | |---|---|---| | `render` | after the behaviours; the formulas are MathML already. A listener may return a promise, which the runtime awaits before `math` (an add-on that renders math itself does it here) | the root: `main.luccet`, or the element given to `luccet.render` | | `math` | right after the `render` listeners have settled: the formulas are final | the root | | `ready` | once, after the first `render` and `math` and the scroll to the URL's fragment | `main.luccet` | | `diagnostic` | for each runtime diagnostic reported after you subscribe: `addon.failed`, `script.document-write`, `script.domcontentloaded`, `doc.quirks` | the diagnostic object | ::: - `on` returns a function that unsubscribes `fn`. - Any other event name throws a `TypeError`. - `render` and `math` fire again at every `luccet.render`. `ready` fires once: a listener added after it never runs, so use the promise `luccet.ready` instead ([`luccet.ready`](api.html#ready)). - An error in a listener is caught and logged. - Under node nothing fires. [The runtime lifecycle](api.html#lifecycle) shows where each event falls. ### Patterns {#patterns} #### An interactive element {#pattern-interactive} A spoiler: an inline element that is a real button, hidden until pressed. The schema gives the element, its attributes, its look and its behaviour. ```html <script> window.LUCCET = {schema: {inline: {hide: { tag: 'button', attrs: {type: 'button', 'aria-pressed': 'false'}, css: '.luccet .hide[aria-pressed="false"] { color: transparent; background: var(--t-fg); }', dom(el) { el.addEventListener('click', () => { el.setAttribute('aria-pressed', el.getAttribute('aria-pressed') === 'true' ? 'false' : 'true'); }); }, }}}}; </script> ``` `The answer is :hide[42].` renders as `<button class="hide" data-t="hide" type="button" aria-pressed="false">42</button>`. Because it is a `<button>`, it is focusable and works from the keyboard with no extra code. #### Reading `data-*` attributes and raw bodies {#pattern-data} A behaviour reads its options from the element. Attributes written in braces arrive as written, so `el.dataset` holds them: ```luccet ::countdown{data-to=2026-12-31 data-label="New year"} ``` ```js luccet.define('countdown', (el) => { const days = Math.ceil((new Date(el.dataset.to) - Date.now()) / 864e5); el.textContent = `${el.dataset.label}: ${days} days`; }); ``` For more than a few values, give the container a raw body (`{raw}`, or `body: 'raw'` in its entry). The behaviour reads it as `el.textContent`: ```luccet :::chart{raw} month,rain Jan,62 Feb,48 ::: ``` ```js luccet.define('chart', (el) => { const [head, ...rows] = el.textContent.trim().split('\n').map((line) => line.split(',')); // … draw the chart from head and rows, then replace el's content }); ``` No schema entry is needed: `::countdown` and `:::chart` already carry their `data-t`. #### Behaviours that need rendered math {#pattern-math} The formulas are MathML when the note mounts, so a behaviour already sees each `span.t-math` with its `<math>` element and its TeX in `data-tex`. Code that measures them, or that must also see what an add-on renders itself (the [KaTeX add-on](math.html#katex) does it in a `render` listener), listens for `math`: ```js luccet.on('math', (root) => { for (const eq of root.querySelectorAll('.t-eq')) { eq.classList.toggle('wide', eq.scrollWidth > eq.clientWidth); } }); ``` - `math` fires on `main.luccet` once the `render` listeners have settled, and again with its root at each `luccet.render`. So work inside `root`. - Each formula's TeX is in its `data-tex` attribute. A formula that does not translate has the class `t-error` and shows its TeX as text. To render new Luccet content into a part of the page, as a live preview does, use `luccet.render(root, source)`: its formulas are MathML too, and it runs the behaviours on the new elements ([`luccet.render`](api.html#render)). ## Custom transforms {#transforms} A transform computes something from the whole note before it is written: a glossary, an index, a count, a check. It works on the AST, so its result is in the HTML from the start, in the browser and in `luccet.toHTML`. :::syntax ```js const remove = luccet.transform(name, fn, {before: 'refs'}) // or {after: 'numbering'} // fn(ast, ctx), with ctx = {schema, opts, lang, report} ``` ::: - **`name`**: a non-empty string that is not a built-in transform's name. Registering a name again moves it and replaces its function. - **Where it runs:** `{before: 'x'}` or `{after: 'x'}`, where `x` is any transform already registered. Without either, it runs last. An unknown `x` throws. - **`remove()`** takes it out. A `remove` from an earlier registration of the same name does nothing. - **`fn(ast, ctx)`** changes `ast` in place. Its return value is ignored. - **A transform that throws** is skipped, and the note renders without it. It is reported as `addon.failed`, an error at line 0: "the transform "NAME" threw: MESSAGE". - **Once per tree.** A tree is transformed once; transforming it again returns it unchanged. :::table[The built-in transforms, in order]{#tbl-transforms} | Transform | Does | So a transform placed after it sees | |---|---|---| | `figures` | turns an image with an id into a `figure` container | implicit figures as containers | | `tables` | merges a `table` container with its pipe table | merged tables | | `attributes` | resolves elements, title slots, schema `class` and `attrs`, reserved keys | `data.luccet.tag`, `data.luccet.slot` | | `footnotes` | numbers footnotes, `fn-`/`fnref-` ids | footnote numbers | | `ids` | the id registry, heading slugs, invalid and duplicate ids | every heading's id | | `numbering` | counters, labels, equation numbers | `data.luccet.number`, `data.luccet.text` | | `refs` | fills references, checks fragment links | reference text | | `toc` | fills `toc` leaves | tables of contents | | `meta` | the title fallback | `data.luccet.meta.title` | ::: So a transform that adds ids or headings runs **before `ids`**: then references to its ids resolve, and its headings get slugs and enter the table of contents. One that reads numbers runs **after `numbering`**. [The transformed AST](api.html#transformed-ast) lists every field the built-in transforms write. **`ctx`:** - `ctx.schema`: the registry in use; - `ctx.opts`: the options of the call (`head`, `lang` …); - `ctx.lang`: the label language ([Labels in other languages](#languages)); - `ctx.report(code, at, message, hint, severity)` adds a diagnostic. - `at` is a node (its position is used) or a position `{start, end}`; without one, line 1, column 1. - `severity` is `'error'`, `'warning'` (the default) or `'info'`. A code of Luccet's own keeps its own severity, so name yours after your add-on: `glossary.empty`. - Your diagnostics reach `luccet.check`, `luccet.diagnostics`, the console and the panel like Luccet's. ### A worked transform {#glossary} A glossary: `:term[…]` marks a term, and a `::glossary` leaf lists every term once, sorted, each linking to its first use. ```js [glossary.js, an add-on with a transform]{#lst-glossary} (function () { 'use strict'; const luccet = window.luccet; luccet.inline('term', { tag: 'dfn' }); luccet.leaf('glossary', { tag: 'nav' }); const text = (nodes) => nodes.map((n) => n.value || (n.children ? text(n.children) : '')).join(''); luccet.transform('glossary', (ast, ctx) => { const terms = new Map(); // term -> the id of its first use const lists = []; luccet.visit(ast, (node) => { if (node.type === 'leafDirective' && node.name === 'glossary') lists.push(node); if (node.type !== 'textDirective' || node.name !== 'term') return; const word = text(node.children).trim(); if (!word) return ctx.report('glossary.empty', node, 'this term is empty', 'write the term in the brackets: :term[kernel]'); if (terms.has(word)) return; const a = node.attributes || (node.attributes = {}); if (a.id === undefined) a.id = `term-${terms.size + 1}`; terms.set(word, a.id); }); if (terms.size && !lists.length) ctx.report('glossary.missing', null, 'the note has terms but no ::glossary', 'add ::glossary where the list goes', 'info'); const items = [...terms.keys()].sort((a, b) => a.localeCompare(b)).map((word) => ({ type: 'listItem', spread: false, checked: null, children: [{ type: 'paragraph', children: [{ type: 'link', url: `#${terms.get(word)}`, title: null, children: [{ type: 'text', value: word }] }] }], })); for (const leaf of lists) leaf.children = [{ type: 'list', ordered: false, start: null, spread: false, children: items }]; }, { before: 'ids' }); })(); ``` With it, `A :term[kernel] is a set; so is the :term[image].` followed by `::glossary` renders as: ```html <p>A <dfn id="term-1" class="term" data-t="term">kernel</dfn> is a set; so is the <dfn id="term-2" class="term" data-t="term">image</dfn>.</p> <nav class="glossary" data-t="glossary"><ul> <li><a href="#term-2">image</a></li> <li><a href="#term-1">kernel</a></li> </ul> </nav> ``` - It runs **before `ids`**, so the ids it gives the terms are registered: the links are checked like any fragment link, and `@term-1` would resolve. - It walks the tree with [`luccet.visit`](api.html#visit), which an add-on has under node too ([Under node](addon-api.html#node)). So it runs in the browser, in `luccet check` and in `luccet build` alike. - The nodes it builds are mdast nodes ([Node types](api.html#node-types)); the emitter writes them like parsed ones. They have no positions, so they get no `data-pos`. - An empty `:term[]` gets `glossary.empty` (warning) at the term. ### When to use a transform {#when-transform} Use a transform when: - the result depends on the whole note (counts, indexes, cross-references); - it must be in the HTML before any script runs, with no flash of unfinished content; - it must be in `luccet.toHTML`'s output. Use a behaviour when the work needs the page: events, measurement, a widget, data fetched at run time. Where transforms run: - **in the browser**, once per tree: at mount, and at each `luccet.render(root, source)`; - **under the command line and the language server**, from an add-on: `luccet check` reports their diagnostics, and `luccet build` writes their changes into the page ([Under node](addon-api.html#node)); - **under node, in your own script**: a transform registered with `require('./luccet.js').transform(…)` runs in `toHTML`, `check` and `transform`. ## Styling {#styling} ### Classes and attributes {#classes} Every element Luccet writes carries classes and attributes to key CSS on. The look is a [theme's](#themes). The custom properties on `:root` are the contract between them: `luccet.css` draws its own parts with them, add-ons read them, and a theme sets them. Their defaults are the system's colours, or `luccet.css`'s own where the system has none. :::table[Custom properties]{#tbl-properties} | Property | Light | Dark | Used for | |---|---|---|---| | `--t-bg` | `Canvas` | | the page as the browser draws it: the diagnostics panel; a theme's page | | `--t-fg` | `CanvasText` | | the text | | `--t-muted` | `CanvasText` | | line numbers; quotes, captions and equation numbers in a theme (the system's `GrayText` is too faint for text in some browsers) | | `--t-line` | `GrayText` | | rules and borders in a theme | | `--t-line-strong` | `GrayText` | | a control's border, 3:1 against the page: the diagnostics panel; `kbd` and a search box in a theme | | `--t-soft` | `ButtonFace` | | code backgrounds and table headers in a theme | | `--t-link` | `LinkText` | | links in a theme | | `--t-mark` | `#fff2a8` | `#5c4d00` | highlighted code lines; `==highlight==` in a theme, where text in it is `--t-fg` (a plain note's highlight is the browser's) | | `--t-error` | `#b3261e` | `#ffb4ab` | `.t-error` text and border, the panel | | `--t-error-bg` | `#fdecea` | `#3b1714` | `.t-error` background | | `--t-warn` | `#8a5300` | `#e3b341` | warnings in the panel | | `--t-sans` | `system-ui, sans-serif` | | the panel; headings and table headers in a theme | | `--t-mono` | `monospace` | | `.t-error`; code in a theme | | `--t-math` | `"Latin Modern Math", "STIX Two Math", "Cambria Math", "Libertinus Math", "TeX Gyre Termes Math", "DejaVu Math TeX Gyre", "Noto Sans Math", math` | | the math font of every formula's `<math>`: a font with OpenType's math table, so brackets stretch and big operators grow ([fonts](math.html#browsers)). With a theme, set its properties instead. A style in the head, before the luccet.js line, is enough: ```html <!doctype html><meta charset="utf-8"><style> body { max-inline-size: 42rem; margin-inline: auto; font: 1.1rem/1.6 Georgia, serif; } </style><script src="luccet.js"></script> ``` ```html <!doctype html><meta charset="utf-8"><style> :root { --t-width: 48rem; --t-font: "Iowan Old Style", Georgia, serif; --t-link: #8a3ffc; } </style><script src="luccet.js" data-use="https://cdn.jsdelivr.net/gh/Luccet/themes@1/classic.css"></script> ``` **The cascade.** Luccet's stylesheets form one group in the head, placed before the head's first stylesheet of your own, in this order: 1. the base, `luccet.css`; 2. each add-on in `data-use` order: a CSS add-on's link, or the `luccet.style` sheets a script add-on adds; 3. other `luccet.style` sheets: from `window.LUCCET.schema` entries, from note scripts. Your own head styles come after the group, and a `<style>` written in the note after that. So at equal specificity, **your CSS wins** over Luccet's and over every add-on's. Ways to add your own CSS: - a `<style>` or `<link rel="stylesheet">` in the head, before the luccet.js line; - a `<style>` block in the note, as raw HTML; - a CSS add-on: `data-use="theme.css"`, ordered among the add-ons, such as one of Luccet's [themes](#themes); - `luccet.style(css)` from a script; - a schema entry's `css`. ### `luccet.style` {#style-api} :::syntax ```js luccet.style(css) // adds a <style> to the head; returns it ``` ::: - **While an add-on runs,** the sheet goes to that add-on's place in the cascade (rule 3 above). Otherwise it goes after all add-ons (rule 4). - **Each call** adds one `<style>`. With `data-nonce`, it carries the nonce, so a strict CSP allows it ([CSP](publishing.html#csp)). - A schema entry's `css` goes through `luccet.style`. - **Under node** it does nothing and returns nothing. ### Dark mode {#dark-mode} - **A plain note follows the reader's system setting**: `luccet.css` sets `color-scheme: light dark`, so the browser draws the page light or dark, and the colour properties default to the system's colours, which follow. Its own colours (errors, code, highlighted lines) have dark values inside `@media (prefers-color-scheme: dark)`. - **The browser's own parts.** luccet.js adds `<meta name="color-scheme" content="light dark">` unless the head has one, so form controls and scrollbars match from the first paint. - **Restyling dark mode only:** set your values inside the same media query: ```css @media (prefers-color-scheme: dark) { :root { --t-bg: #0d1117; --t-link: #79c0ff; } } ``` - **A property set outside a media query holds in both modes**, since your CSS comes later. Set some colours that way and not the others, and the others still switch: light text can end up on your light background. Set the whole palette, or set it per mode. - **One palette for every reader:** set `color-scheme: light` (or `dark`) on `:root`, and every colour property at the top level. A `color-scheme` key in `:::meta`, or a `<meta name="color-scheme">` in the head, sets only the browser's own parts. ### Themes {#themes} The look is a theme's, and Luccet's live in their own repository, [Luccet/themes](https://github.com/Luccet/themes). A theme is a stylesheet [add-on](#addons): list it in `data-use`, from jsDelivr or as a copy next to the note. - **`classic.css`** is the reading column, the type and the palette `luccet.css` drew before 2.0, light or dark. - **Colour themes** after well-known editor palettes: Catppuccin, Dracula, Everforest, GitHub, Gruvbox, High contrast, Kanagawa, Monokai, Nord, One, Rosé Pine, Sepia, Solarized and Tokyo Night. Listed after `classic.css`, one changes its palette and keeps the rest; on its own, it colours a plain note: its background and text, links and highlights. ```html <!doctype html><meta charset="utf-8"><script src="luccet.js" data-use="https://cdn.jsdelivr.net/gh/Luccet/themes@1/classic.css https://cdn.jsdelivr.net/gh/Luccet/themes@1/nord.css"></script> ``` The repository's README lists every theme and its files. Pin a release of the themes (`@v1.0.0`) to be sure; `@1` follows the fixes of a major. - **A colour theme with both modes has three files.** `NAME.css` follows the reader's system setting. `NAME-light.css` and `NAME-dark.css` give every reader one palette. A theme with one mode is one file, the same for every reader. - **Your CSS still wins.** A theme cascades after luccet.css and before your own styles ([Overriding them](#overriding)): set a property yourself to change one colour of a theme. - **Readable.** Every theme reaches 4.5:1 for every text colour (WCAG AA), 7:1 in High contrast, a control's border 3:1, and answers `prefers-contrast: more`; the themes repository checks each one. Print and forced colours are `luccet.css`'s ([Print](#print)), whatever the theme. - **Your own theme.** A theme is a stylesheet that sets the colour properties on `:root`, and again under `@media (prefers-color-scheme: dark)` for a dark mode, and styles the page with them: copy one of the themes and change its values. - **A math font.** A theme may also set `--t-math`, to put a math font of its own first, one it loads with `@font-face`, for readers whose system has none ([fonts and browsers](math.html#browsers)). ### Print {#print} `luccet.css` has a print stylesheet: - the page prints dark on light: `color-scheme` is `light` and every colour property of `luccet.css` ([Custom properties](#custom-properties)) takes its light value (the system's light colours, `luccet.css`'s own for errors and highlights), `!important`, so a dark theme or a reader in dark mode still prints on white, and no theme has to repeat this. These are the page's colours: an add-on's own, such as the code add-on's `--t-code-*`, are not among them; - code wraps, and tables, code and equations no longer scroll; - the diagnostics panel is hidden. The rest is a theme's: `classic.css` drops its column limit and padding in print, sets `--t-size` to `11pt`, and keeps paragraphs, headings, figures and equations whole across page breaks. Before printing, luccet.js opens every `details.t-block` (closing them again afterwards). Formulas need nothing: they are MathML from the start. To change print, write `@media print` rules. To print a colour property your own way, set it `!important` there: ```css @media print { :root { --t-link: #000 !important; } .callout-toggle { display: none; } } ``` ## Labels in other languages {#languages} ### Language maps {#label-maps} A `label` can be a map from language tags to words: ```js luccet.block('lemma', { counter: 'theorem', label: { en: 'Lemma', de: 'Hilfssatz', fr: 'Lemme', 'pt-BR': 'Lema' } }); ``` The label is picked when the note is rendered, and the reference text follows it: in a German note, `:::lemma{#l}` is "Hilfssatz 1", and so is `@l`. ### How the language is chosen {#choosing-language} In the browser, and in `luccet check`, `luccet build` and the language server, the first of: 1. `data-lang` on the luccet.js tag; 2. `window.LUCCET.lang`; 3. `lang` in a top-level `:::meta`; 4. `lang` on `<html>` in the head. When the head's `<html lang>` and `:::meta` disagree, the head wins, with `meta.conflict` ([Metadata](elements.html#metadata)). In your own node script, `luccet.toHTML`, `luccet.check` and `luccet.transform` read their `lang` option, then `:::meta`, then the `<html lang>` of their `head` option. ### Matching an entry {#matching} Language tags compare without regard to case. Given the language, the map's entry is the first that matches: 1. the exact tag: `pt-BR` for `pt-BR`; 2. its primary subtag: `pt` for `pt-BR`; 3. any entry with that primary subtag: `pt-PT` for `pt-BR`; 4. `en`; 5. the map's first entry. With no language at all, `en`, then the first entry. Values that are not strings are skipped. **A label function** receives no language. To translate a computed label, keep a map of words and pick from it yourself, or use a map and no function. ## The demo schema {#demo-schema} The live examples with `schema=demo`, on this page and every other, render with this schema.
